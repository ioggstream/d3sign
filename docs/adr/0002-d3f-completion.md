# 4. D3FEND Graph Editor Completion

Date: 2026-07-09

## Status

Accepted

## Context

When modifying the mermaid diagram in the editor,
I expect to have a completion suggestion, like the one
provided by <https://github.com/ioggstream/vscode-d3fend-language>.

Alternatives:

- use vscode-d3fend-language extension for completion suggestions, but this would require switching the editor to Monaco, which is the editor used in VSCode and supports the Language Server Protocol (LSP)

- use a custom completion provider.

- reuse the existing d3fend ontology JSON projections to provide completion
  suggestions for d3fend classes and properties, though vscode-d3fend-language
  is a very comprehensive solution.

Elements:

- what are the performance implications?

## Decision

- [x] The editor will provide completion suggestions for d3fend classes and properties, based on the d3fend ontology.
- [x] The completion data is generated from
  `d3fend.ttl` by a build script, following the
  convention the other D3FEND data files in this repo
  already use.
- [x] Alongside completion the editor offers one hover
  card per `d3f:` term, from the same data file. It
  carries the definition, the ancestor path and the
  inverse/parent/child relations, the relations as
  buttons that redraw the card for that term — so
  browsing the hierarchy is hovering, with no second
  panel to open or dismiss.

## Consequences

Pros:

- No architecture change required — editor stays CodeMirror 6, no Monaco/LSP.
- Static JSON data, no runtime RDF parsing; matching is a linear filter over
  a few thousand entries, negligible cost in a browser.
- Full feature parity with `vscode-d3fend-language` (completion, hover,
  inverse-of/parents/children, transitive/symmetric markers, interactive
  hierarchy browsing) without a runtime dependency on that project — and in one
  surface rather than two, so nothing has to be kept in sync by hand.
- Data generation follows the project's existing
  convention, so no new tooling pattern is introduced.

Cons:

- The completion data file must be regenerated
  whenever `d3fend.ttl` changes. This is the
  maintenance cost already accepted for the other
  generated D3FEND data
  ([ADR 0008](0008-show-node.md)).
- It ships committed as an empty placeholder until
  someone runs the build script against a local
  `d3fend.ttl`; completions are silently absent until
  then.

## DONTREADME

Notes for LLM agents. They describe the code as it
is, not the decision, and go stale: check the code
before trusting them.

- Editor side, all under `app/src/editor/`:
  `d3fendCompletion.js` (completion source),
  `d3fendHover.js` (the hover tooltip, and `Escape` to
  dismiss it), `d3fendCard.js` (the card's DOM, whose
  relation buttons redraw it in place),
  `d3fendHierarchy.js` (the data: `termSections` and
  the `hierarchyText` flattening of it that the
  completion popup's `info` pane needs).
- There is no `d3fendHierarchyPopover.js` any more: a
  hover tooltip stays open while the pointer is inside
  it, so the card itself is the hierarchy browser and
  the separate `Mod-Alt-h` / Mod-click panel that used
  to duplicate its content is gone.
- The completion list is **not** CodeMirror's popup:
  `d3fendCompletion.js` only supplies the options, and
  `completionPanel.js` draws them as a `showPanel` strip
  at the top of the editor, with the selected term's
  hierarchy beside the list. The popup is suppressed
  (`display: none` in `editorTheme.js`). A panel is laid
  out by the browser and cannot be mispositioned or
  clipped; the popup is a tooltip, and every tooltip
  here is positioned by measurement, which is how the
  list ended up invisible while the completion session
  itself was working.
- The hover card is still a tooltip, rendered into
  `#cm-tooltip-host` — a fixed, zero-size element
  `editorPane.js` appends to `<body>` and `app.css`
  styles. Not `<body>` itself: CodeMirror appends one
  container per editor to the parent it is given, and
  `body` is a clipped `100vh` box, so an in-flow
  container lands below the viewport's bottom edge.
- They all read
  `app/src/data/d3fend-completions.json`, generated by
  `app/scripts/build-d3fend-completions.py /path/to/d3fend.ttl`.
- That script follows the rdflib pattern of
  `build-d3fend-metadata.py` and
  `build-d3fend-categories.py`, whose outputs
  (`d3fend-metadata.json`, `d3fend-categories.json`)
  carry the same regeneration cost.
- `getItem` and the `parents` field of the same data
  file are reused by the graph's icon resolution
  ([ADR 0015](0015-graph-visualization-preferences.md)).
